动画同步组（Animation Sync Group）

我们会在动画混合的时候碰到一个非常常见的问题：如果我在一个动画迈左腿的时候，混合了另一段动画，另一段动画是从迈右腿开始的，这个时候，我的人物因为混合的缘故，会变得双脚并拢。然而我实际希望的可能是自然地过渡。

如果没有同步组的话，上面这个问题的解决方法一般就是只允许在某些时间段进行混合，也就是如果我从走路的动画过渡到跑步动画的话，必须等我左脚完全走完，到了迈右腿的时候才进入混合。给人一种粘滞的感觉，这可给恶心死了。

因此，我们很容易就想到，既然混合的本质是每一帧把两个动画的当前姿态进行混合，那只要找到进入混合的动画和当前播放的动画接近的姿势，从这里开始进行混合不就可以了吗？

上面就是动画同步组的核心思想了。

一、核心概念

动画同步组的核心目标是：确保组内所有动画片段在播放时保持时间轴对齐。

在实际应用中，以下场景通常需要同步组：

  • 分层动画混合：上半身与下半身各播放不同动画，但需要节奏一致
  • 多角色协同：多个角色执行配合动作（如双人近战格斗）
  • 动画状态机同步：多个 Animator 之间的状态切换需要保持同步

当然，同步组在实际使用的过程中也会遇到各种乱七八糟的神奇问题，可能有的是：

  • 动画相位长度不同：多个动画之间，起始的脚步，动画的速度，走了几步都完全不一样
  • 不同同步组打架：多个动画配置了同步组，实际运行起来可能找不到实际用哪个，导致争抢
  • 不同切换导致抖动：同步组需要每一帧设置leader和follower，如果在一些极端情况下两者的身份不断转变，就会导致动画不停跳变

接下来我们将看看在unity里怎么实现。

二、底层实现原理

2.1 双层架构

同步组的实现分为 C# 托管层 和 C++ 原生层 两部分。C# 层负责每帧收集成员信息并注册，C++ 层在 FK（Forward Kinematics）pass 内执行真正的 Leader 选举和 Follower 对齐——此时 PlayableGraph::PrepareFrame 已完成时间推进，但采样 Job 尚未构建，因此 Follower 的 SetTime/SetSpeed 能在本帧采样前生效，消除了旧 C# LateUpdate Resolve 方案的一帧相位滞后。

C# 托管层关键类：

类 职责
SyncGroupManager 全局管理器，每帧 BeginFrame → Register*Member → PushToNative → SyncBackEvaluatorTimes
SyncGroupState 单个同步组的运行时状态，维护成员列表和上一帧 Leader 句柄
SyncGroupMember 成员结构体，记录 weight、clipLength、originalSpeed、syncRole、markerTrack 等
SyncMarkerTrack 标记轨道，将动画时间映射为标记感知相位，支持 EvaluatePhase/EvaluateTime/EvaluateSegment

C++ 原生层关键类：

类 职责
AnimGraphSyncGroupResolver 原生解析器，执行 Leader 选举与 Follower 同步的核心算法
AnimGraphSyncRole 角色枚举（CanBeLeader/AlwaysFollower/AlwaysLeader/TransitionLeader/TransitionFollower）

2.2 每帧生命周期

同步组的数据是每帧重建的——m_Members、m_MarkerTimes、m_MarkerPhases、m_MarkerIndices 在 BeginFrame 时清空，然后由 C# 逐个注册。跨帧持久化的只有 m_GroupLeaders（Leader 迟滞）和 m_DrivenTimes（连续时间追踪）。

2.5 驱动模式

同步组根据成员类型和配置，选择两种驱动模式：

条件 驱动模式 说明
Evaluator 成员 SetTime（driveByTime=true） Evaluator 的时间由显式 API 控制
带标记轨道的成员 SetTime（driveByTime=true） 标记同步需要精确对时
timeDrivenExternally SetTime（driveByTime=true） 状态机驱动的 Clip，SetSpeed 无效
其他普通 Clip/BlendTree SetSpeed（driveByTime=false） 速度追赶，渐进收敛

关键设计：timeDrivenExternally

状态机每帧通过 SetTime 推进 Clip 时间，这使得 SetSpeed 对其无效（下一帧又被状态机覆写）。因此这类成员一旦进入同步组，driveByTime 强制为 true，同步组用 SetTime 接管其时间。更重要的是，timeDrivenExternally 成员被 resolver 驱动过后，即便组退化为单成员也继续自驱——因为外部时间线在被覆盖期间独立自转，此刻交还必然一次性清算两线分叉，产生全权重跳变。

三、同步策略与权重计算

3.1 Leader 选举

同步组采用 Leader-Follower 模型：每帧从组内选出一个 Leader，其时间/相位作为基准，其余成员（Follower）向 Leader 对齐。

选举优先级如下：

  1. AlwaysLeader（最高优先级）：直接当选，不参与权重比较
  2. 按权重选取：从 CanBeLeader 和 TransitionLeader 角色的成员中，选 weight 最大的
  3. 全为 AlwaysFollower 的回退：如果没有任何成员可以当 Leader，回退到 members[0] 并输出警告

迟滞机制（Hysteresis）：

Leader 频繁切换会导致 Follower 不断重新对齐，产生抖动。为此引入了迟滞阈值 kHysteresisThreshold = 0.1：

只有当新候选者的权重显著超过旧 Leader（超过 10% 的余量）时，才会发生 Leader 切换。这有效避免了过渡期间两个权重接近的动画来回抢占 Leader 身份的问题。

3.2 三种相位同步策略

根据成员是否拥有标记轨道、以及标记是否具有语义索引，同步组自动选择三种同步策略中最合适的一种：

策略一：线性相位同步（无标记）

当成员没有标记轨道时，使用最简单的线性相位：

  • Leader 的 phase = time / clipLength
  • Follower 通过 EvaluateTimeFromPhase(leaderPhase) 计算 targetTime = leaderPhase × followerClipLength
  • 然后 SetTime(targetTime) 或通过速度追赶收敛

局限：无法处理步频不同、起始脚步不同的动画——两段都是走路的动画，一段迈左腿开始、另一段迈右腿开始，线性相位会把它们对齐到错误的位置。

策略二：标记感知相位同步（Marker-based）

当成员有标记轨道但没有有意义的语义索引时（所有 markerIndex 相同），使用标记感知的相位映射：

  • 正向映射（ComputePhase）：当前时间 → 相位，在相邻标记间线性插值
  • 反向映射（EvaluateTimeFromPhase）：目标相位 → 时间，二分查找相位所在的标记段，然后在段内反插值

这样即使两段动画的步频不同，只要在左脚着地和右脚着地处放了标记，相位映射就能正确反映运动进度。Leader 在”左脚着地”的相位，Follower 也会被 SetTime 到自己的”左脚着地”时刻。

策略三：语义段落同步（Index-based）

当 Leader 和 Follower 都有有意义的语义索引（至少 2 个不同的 markerIndex 值）时，启用最强的同步策略——按 (fromIndex → toIndex) 语义段落匹配：

  1. Leader 计算当前所在段落的语义信息：(fromIndex, toIndex, localProgress)
  2. Follower 在自己的标记轨道中查找所有匹配 (fromIndex → toIndex) 的段落
  3. 在匹配段落中，选目标 Phase 最接近 Leader Phase 的（主判据），相位等距时选离当前时间最近的（副判据，保证连续性）
  4. SetTime 到该段落内 localProgress 对应的时间

为什么需要语义段落匹配？

考虑一段走路（左→右→左→右）和一段跑步（左→右→左→右），如果走路的”左→右”段落和跑步的”左→右”段落在 Clip 中的时间位置完全不同，仅靠相位数值匹配可能把 Leader 的”左→右”段对齐到 Follower 的”右→左”段——姿态完全错位。语义索引确保了”左脚着地→右脚着地”这个运动语义在所有动画中被匹配到同一段落。

3.3 速度追赶（Speed Catch-up）

对于不带标记、且时间不由外部驱动的普通 Clip/BlendTree 成员，同步组使用速度追赶策略——不直接 SetTime（避免跳变），而是调整播放速度让 Follower 的相位逐渐收敛到 Leader：

kCatchUpRate 2.0 相位误差到速度调整的增益系数。误差 0.1 → 速度偏差 20%

3.4 SetTime 驱动与推进钳制

对于 driveByTime = true 的成员（Evaluator、带标记的 Clip、状态机驱动的 Clip），同步组直接用 SetTime 对齐。但这里有一个关键问题：Leader 交接或标记段落重排会让对齐目标单帧偏移 1/4~1/3 周期，直接 SetTime 过去在权重不为零时是可见的姿势跳变。

为此引入了 Follower 推进钳制（ClampFollowerAdvance），仅在循环动画的连续驱动帧（wasDrivenLastFrame = true）生效：

常量 值 作用
kFollowerMinAdvanceRate 0.5 最小推进倍率（至少以半速前进）
kFollowerMaxAdvanceRate 2.0 最大推进倍率（最多以 2 倍速追赶）

入组首帧例外：wasDrivenLastFrame = false 时不钳制，保留硬对齐语义——第一次进入同步组时必须立即对齐到正确相位。

3.5 连续时间与 Root Motion

循环动画的 SetTime 会让时间回绕到 [0, clipLength)，但 Root Motion 需要连续的时间差（deltaTime = currentTime - previousTime）。GetContinuousTargetTime 将目标时间展开到一条不回绕的连续时间线上：

  1. 取目标时间在当前周期内的值 targetInCycle
  2. 以 lastResolvedTime（或当前 playable->GetTime()）为参考，找到最近的周期
  3. 如果 delta > clipLength × 0.5，说明目标在前一个周期，减去一个 clipLength
  4. 首帧防回退：如果首帧被驱动（如 Leader 切换后原 Leader 变 Follower），且对齐目标在当前时间之前，钳制到当前时间——避免 Root Motion delta 为负导致角色瞬移后退

3.6 单成员组的持续维护

当组退化为单个成员时（如过渡结束、其他成员权重归零退出），ResolveSingleMember 仍然执行：

  • timeDrivenExternally 成员继续自驱：被 resolver 驱动过的成员不会把时间交还给外部系统，避免两线分叉的跳变
  • 维护组级同步位置：单成员期间持续更新 GroupLeader 的 syncPrevFootId/syncNextFootId/syncPositionBetween，这样其他成员重新进组时可以无缝衔接
  • 维护 lastPhase：保持跨帧相位连续性，下次组重新出现多成员时 Follower 对齐有基准

3.7 权重在同步中的角色

权重在同步组中有两个关键作用：

  1. Leader 选举：权重最大的 CanBeLeader 成员优先当选。过渡期间，新状态的权重逐渐升高、旧状态的权重逐渐降低，Leader 身份会在权重交叉超过迟滞阈值后自然切换。

  2. 不影响 Follower 对齐精度：Follower 无论权重多低（只要 > 0 且在组内），都会被完全对齐到 Leader 相位。权重只决定混合时的”可见程度”——权重为 0.1 的 Follower 即使被 SetTime 拉到正确相位，对最终姿态的影响也很小，但一旦权重升高，它已经在正确位置了，不会产生跳变。

这种设计确保了：过渡开始时 Follower 就已经同步到位，随着权重升高自然平滑地接管姿态，无需等到权重足够大才开始对齐。

4.1 基本配置

五、注意事项与最佳实践

5.1 标记配置

  • 标记必须覆盖整个循环周期：最后一个标记到 Clip 结尾的段落会自动以第一个标记作为虚拟结束标记（跨 loop）
  • markerIndex 要一致：不同动画中相同语义的事件（如”左脚着地”）必须使用相同的 markerIndex，否则只能退化为数值相位同步
  • 至少需要 2 个不同 markerIndex：全部相同时 HasMeaningfulMarkerIndices 返回 false，不会启用语义段落同步

5.2 角色配置

  • AlwaysLeader 谨慎使用：该角色的成员永远不被跟随，如果它和组内其他成员的相位不同步，会导致所有 Follower 持续追赶
  • 过渡场景：过渡中的旧状态设为 TransitionLeader、新状态设为 TransitionFollower 可以控制 Leader 的交接方向
  • 全是 AlwaysFollower 会回退到 members[0]，应避免

5.3 性能考量

  • 每帧成员数通常 < 8，O(n²) 的组聚合扫描开销可忽略
  • 标记数据使用扁平数组（m_MarkerTimes/m_MarkerPhases/m_MarkerIndices）连续存储，cache 友好
  • SyncMarkerTrack.GetNativeMarkerArrays 惰性构建并缓存，避免每帧 GC

5.4 常见问题排查

问题 可能原因 排查方向
混合时双脚并拢 标记未配置或 markerIndex 全相同 检查 HasMeaningfulMarkerIndices
过渡时姿势跳变 Leader 频繁切换 检查迟滞阈值和权重曲线
角色瞬移后退 首帧 SetTime 产生负 delta 检查 GetContinuousTargetTime 的首帧防回退逻辑
非循环动画播完卡住 播完后取模得到虚假相位 检查非循环成员的跳过逻辑
距离匹配与同步组冲突 hasDesiredTime 的成员不应被 marker 拽走 距离匹配成员的时间是地面真值，同步组不覆写
